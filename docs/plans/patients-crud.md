## 1. Objective & scope

Manage **patients**: register new, look them up by phone, and edit. The **phone lookup
returning multiple patients** and the **create** path are the reusable pieces Part 2
(consultation) will embed.

**In scope**
- `/patients`: **search by phone or name → results list**, **Register patient**, **Edit**.
- Fields: **name** (required), **phone** (required in the form - it's the lookup key),
  **age** (optional), **area** (optional).
- Auto-generated **`patient_code`** (MRN) shown to users. Server-enforced, activity-logged.

**Out of scope** - Part 2 consultations; print/payment; **delete/deactivate** (patients
have no `active` column and are never deleted - edit only). See §10.

## 4. Decisions (firm)

**A. `patient_code` generated by the DB (race-free), via migration `0004`.** Add a
sequence + column default so every insert gets a unique MRN with no app logic:
```sql
-- 0004_patient_code.sql
CREATE SEQUENCE patient_code_seq;
ALTER TABLE patients
  ALTER COLUMN patient_code
  SET DEFAULT 'LL' || lpad(nextval('patient_code_seq')::text, 6, '0');   -- e.g. LL000001
```
`createPatient` inserts **without** `patient_code` and `RETURNING id, patient_code` to show
the assigned MRN. (`'LL'` = Life Line; a per-location prefix is a later concern.)

**B. Phone is required in the form** (it's the lookup key), even though the column is
nullable. Validate digits; **do not** make it unique - duplicates across patients are
expected and correct (mother + child).

**C. Two lookup functions** (Part 2 depends on the first):
  - `findPatientsByPhone(phone)` - **exact** phone match, returns **all** rows (the
    "type a number → list of N patients → pick one"). This is what the consultation reuses.
  - `searchPatients(q)` - for the management screen: phone **prefix** OR name `ILIKE`, a
    reasonable `LIMIT`. Ordered by name.

**D. No delete / no deactivate.** No `active` column; patients are permanent. Edit only.
New patient's `location_id` = the creating user's (reuse `getUserLocationId`).

### `lib/patients/schema.ts` (client-safe)

```ts
import { z } from "zod";
const id = z.string().regex(/^\d+$/, "Invalid id.");            // patients.id is BIGINT (string)
const name = z.string().trim().min(1, "Name is required.").max(100);
const phone = z.string().trim().regex(/^\d{7,15}$/, "Enter a valid phone number (7-15 digits).");
const age = z.union([z.coerce.number().int().min(0).max(130), z.literal("")]).optional(); // optional
const area = z.string().trim().max(100).optional().or(z.literal(""));

export const newPatientSchema    = z.object({ name, phone, age, area });
export const updatePatientSchema = z.object({ id, name, phone, age, area });
export type NewPatientValues = z.infer<typeof newPatientSchema>;
```

### UI

- `page.tsx` (server): `await requireAdmin()`, render `<PatientsManager />` (this screen is
  search-driven - it does **not** preload all patients; the table grows large over time).
- `patients-manager.tsx` (client): a **search input** (phone/name) + **Register patient**
  button. Typing queries `searchPatients` (via a small server action or a route) and shows
  a **results table**: `Patient ID (patient_code) · Name · Age · Phone · Area · Added`.
  Empty state before searching ("Search by phone or name") and for no results. Row → Edit
  dialog. **Phone column shows that one number can list several people** - that's expected,
  not a bug.
- `patient-form-dialog.tsx` (client): shadcn `Dialog` + RHF; fields **Name (autofocus) →
  Phone (`inputMode="tel"`) → Age (optional, `inputMode="numeric"`) → Area (optional)**.
  On register success, toast the new **Patient ID** (`patient_code`). Prefill in edit mode.

> **Note for Part 2:** the consultation screen will reuse `findPatientsByPhone` +
> `createPatient` directly (type phone → list to pick, or show optional name/age/area to
> add a new one). Keep these functions clean and independent of this screen's UI.

## 8. Manual verification
Sign in as admin → `/patients`:
1. **Register** a patient → toast shows an MRN like `LL000001`; row appears on search.
2. Register **two** patients with the **same phone** → searching that phone lists **both**

3. Bad inputs (blank name, letters in phone, age 200) → per-field errors, no write.
4. **Edit** a patient → changes persist.

6. Activity: `patient.create`/`patient.update` rows written (via logActivity/writeAudit).
7. `npm test`, `npx tsc --noEmit`, `npx next build` clean. Light-only; `design-audit` addressed.

## 9. UX & security (non-negotiable)
- `requireAdmin()` inside every action; re-validate with the zod schema on the server.
- **Phone is NON-unique** - never merge/dedupe patients by phone (§3 of PROJECT_OVERVIEW).
- Patient identified by `patient_code`/`id`, never by phone.
- Activity-log every create/update. Never hard-delete. Light theme; colour for status only;
  keyboard-first.
